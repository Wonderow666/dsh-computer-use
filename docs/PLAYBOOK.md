# 操作协议（PLAYBOOK）

> 一句话：**动手前五分钟，把三件事确认清楚——输入是否真的生效、界面有哪些现成的语义入口、交付物到底是哪一份。**
>
> 这份文档不是能力清单，是踩坑记录。每一条都对应一次真实的时间浪费。

---

## 0. 五分钟预检（开新任务前无条件执行）

| # | 做什么 | 怎么判断“可以开工” |
| --- | --- | --- |
| 1 | `computer` `inputcheck` | `landed: true`。否则按 `verdict` 处理：锁屏 → 解锁（判据是输入桌面不是 `Default` **或** `lockAppRunning: true`——锁屏时截图与控件树都正常，只有注入被丢弃，别被“看起来没锁”骗了）；`integrity: LOW` → 引擎不在正常完整性位置；`pointerDrifting` → 有人正在动鼠标，重测 |
| 2 | `windows` → 选定目标 `hwnd`；`geom` | 拿到窗口矩形 + **客户区原点** + dpi + scale |
| 3 | `modals` | 没有待处理的对话框/被禁用窗口 |
| 4 | `screenshot` | 拿到 PNG 路径与 `scale`（屏幕像素 = 图像像素 × scale） |
| 5 | **确认交付物** | 文件名、格式、验收标准由用户确认，**不从文件名推断** |

第 5 条最容易被跳过，也最容易全盘作废：把“指导书”当成“要填的模板”，排版、插图、导 PDF 全是白工。

---

## 1. 坐标：只允许一个空间

- 唯一真值是**截图的物理像素**。图像上量的坐标乘以 `scale` 再使用。
- 能相对就相对：`relx`/`rely` 是目标窗口**客户区**偏移，窗口被移动/最大化/还原后依然有效。绝对屏幕坐标只在一次性操作里用。
- 不要在同一个脚本里混用两套来源。`pwsh` 是 DPI-unaware 的：`GetWindowRect` 在 150% 缩放下给的是**逻辑坐标**（= 物理 ÷ 1.5），拿它当物理像素用，每个点击都会偏。
- 窗口几何会被动改变（还原、拖分隔条、切布局）。**每次动作前重新 `geom`，不要缓存坐标**。

---

## 2. 语义优先，像素兜底

按这个顺序选手段，越靠前越稳：

1. **`invoke`** —— UIA 的 Invoke/Toggle/Select/SetValue。不动鼠标、不抢焦点、不受坐标影响。能用就用。
2. **`find` + `invoke`** —— 按名字找控件，拿到的 `id` 与 `snapshot` 同一套编号，直接喂给 `invoke`。
3. **`hover`** —— 图标式界面（工具栏、设备栏、图纸符号）先悬停读 tooltip。**tooltip 里有权威名称，经常还带快捷键**（例如 `Switches Ctrl+Alt+S`、`Connections Ctrl+Alt+O`）。悬停两秒胜过像素 diff 十分钟。
4. **坐标点击** —— 前三样都不支持时的兜底。点之前先 `hit` 确认那一点下面是什么。

快捷键能替代鼠标的就别用鼠标：菜单项本身把答案写在右边了。

### 2.5 先读文本，再考虑截图

`readtext` 是一次调用读完窗口文字（终端、控制台、编辑器、WinForms、多数 Qt 控件），`waittext --regex` 是“等到某段文字出现”而不是“睡两秒再赌它出现了”。

- **状态判断一律先用 `readtext`/`waittext`**。截图 + 视觉是最后手段：慢、贵，而且我容易把“看不清”当成“没发生”。
- 等提示符、等编译结束、等对话框出现 → `waittext`，别 `wait` 一个拍脑袋的毫秒数。
- 打完字要确认落地 → `type` 加 `verify`：文本没出现就报错，而不是假装成功（输入法组合、密码框、焦点丢失都会被抓住）。返回 `verified: "unavailable"` 说明该窗口没有文本通道，这时才回退到截图核对。
- 出图给人看/进文档 → `screenshot` 加 `trim`，把空白边裁掉（实测同一张控制台截图 678 KB → 12 KB）。**证据图再加 `minBytes`**：屏幕熄灭时 PNG 只有 5 KB，`screenshot` 会以 `the screenshot is only 5708 bytes …` 直接报错，而不是让你把白图插进报告。
- 读不到文本是**正常结论**，不是失败：Chromium 默认不暴露渲染内容，`readtext` 会返回 `strategy: "none"` 和一句 hint，此时按 2 里的语义入口走，再退到截图。

### 2.6 CLI 优先，GUI 只负责取证

- 目标程序只要能用命令行/脚本驱动（服务、shell、编译、网络配置），就**走 CLI**：一次 `readtext` 就能读回结果，不用截图、不用坐标、不受窗口遮挡与锁屏影响。
- GUI 只在两件事上不可替代：**必须点才行的界面**，以及**报告要的过程截图**。
- 把"验证功能"和"拍证据"分开：功能先跑通一遍（记录真实输出），再针对报告需要的画面单独补拍。混在一起做，一次失败就要重拍整条链。

### 2.7 先写计划，再一次执行

一旦你知道"要做什么"（前面几步已经确认过界面、控件、路径），就把剩下几步写成一份 `run` 计划，**一次调用跑完**，而不是一次一个动作、每步截一张图确认。

- 写计划前先 `state`（351–547 字节）：`locked`/`lockAppRunning`/`privileged`/前台/目标几何/该应用的模态框，一次看清。
- 找控件先 `ui`，不要 `snapshot`：同一窗口 3946 字节 vs 26390 字节，而且 `ui` 只列能点的东西。需要父级结构或全树时才 `snapshot`。
- 每一步都要自带"什么算成功"：`wait /提示符/ 8000`、`read`、`invoke`。**不要用 `sleep` 当同步手段**——那是把不确定性换成固定浪费。
- `type` 带上 `verify`，`screenshot` 带上 `minBytes`；计划里默认不 `shot`，只有进报告的画面才拍。
- 计划失败时先读那行报错：它带着窗口当时的尾部文本（`| last text: "…"`）。多数时候这一行就够定位，不用再截一张图。

### 2.8 不确定控件时，请人点一下

遇到"这个图标到底是什么"（工具条、自绘 UI、没暴露文本的控件），不要靠点一下看像素变化来猜，也不要为此连续截十张图。开浏览器面板（`panelPort`）让人点一下那个位置：`/api/hit` 直接返回该点窗口 + 控件（`role` / `name` / `automationId` / `id` 路径），再把这套稳定选择器写进计划或 `profile` 文件。**人的一次点击，换模型后面几十步的确定性。**

### 2.9 先找可执行通道，再考虑界面

任务落在**另一台机器**（虚拟机、远程主机）时，第一件事不是截图，是问“能不能直接跑命令”：

- `targets` 看有没有配好的目标（VMware 虚拟机走 Tools，Linux 主机走 ssh）。
- 有目标就 `exec`：一次调用换回 stdout 尾部 + 真实退出码。`put`/`get` 传脚本与文件。
- 典型场景：服务/网络/包管理/编译/日志——这些根本没有“必须点”的界面，走像素是纯浪费。本项目那次 CentOS 7 上部署 OpenStack，30 分钟 `packstack` 全程只在 5 个必须进报告的画面拍了图，其余都是文本往返。
- 只有三种情况退回 GUI：guest 没有 Tools 也不通 ssh、操作只存在于图形界面、以及**报告要的过程截图**。
- 别把跨机 `exec` 和本机 `blockedProcesses` 混为一谈：后者是给本机注入输入用的护栏。

### 2.10 同一套操作做第二遍，就存成 profile

判断标准很简单：**这套步骤你写过两次，或者打算明天再写一次**，就该进 `profiles` 配置，而不是再写一个一次性脚本。

- `profiles` 里放四样东西：`match`（怎么认窗口）、`aliases`（控件叫什么）、`plans`（已经验证过的步骤）、`notes`（给人看的坑）。
- 存好之后：`state` 会告诉你前台应用命中哪个画像；`run { profile, task }` 一次重放，**窗口由 `match` 自动定位**，计划里不写 hwnd——窗口挪了、缩放了、重开都不影响。
- 别名用 `{{name}}`，只在参数部分展开：`invoke {{saveButton}}` 比 `invoke 0.2.1` 更能扛住界面改版。
- 计划正文不要打印进对话（`profiles` 只回名字）；要看某一份就用 `run` 直接跑，跑挂了再读那份计划。
- 反面案例：本项目早期在 `lab5/`、`lab-linux/` 下堆了几十个一次性 `.mjs`，坐标全写死，面板拖一下就全废。那些文件里**唯一值得留下的就是"这套步骤怎么走"**——正好是 profile 该装的东西。

## 3. 状态安全

- **辅助脚本禁止隐式改窗口状态。** 不要写 `ShowWindow(h, SW_RESTORE)`、不要“顺手”最大化一下。一次隐式还原会让之后所有坐标静默错位。
- 需要前置窗口 → `focus`（四级升级），失败就让它失败并读错误——不要用别的 API 绕过前台锁，那只会换来更难查的问题。
- 游戏、会议、全屏独占：`blockedProcesses` 默认已经挡住 PUBG（`TslGame.exe` / `UnrealWindow`）。
- `dryRun: true` 是免费的：先看它打算发什么 argv、要抢谁的焦点。

## 4. 失败三问（“点了没反应”时按顺序排查）

1. **有模态框吗？** `modals` —— 保存询问、确认删除这类对话框会吞掉之后所有输入。这是第一嫌疑人，不是“应用坏了”。
2. **输入通道还活着吗？** `inputcheck` —— 锁屏 / 低完整性 / UIPI 三种静默失败都会让 `SendInput` 返回成功却什么也不发生。锁屏时**别只看 `locked`**：加看 `lockAppRunning`；如果两个证人互相矛盾，用 `Get-Process LockApp` 直接确认。
3. **几何还对吗？** `geom` + 新截图 —— 窗口被还原过？分隔条被拖过？

拿到结论再换方案。**不要**从一次现象推断“这个功能永久不可用”。

## 5. 交付与报告

- 报告只写**做了什么、测到什么**。不写“因为环境限制所以我换了做法”——临时绕过不是事实。
- 没做到的步骤单列“未覆盖”，并说明原因；**不要用“与 XX 对称”带过**（那是实证缺口，不是省略号）。
- 每步留证据：回读到的文件内容、截图路径、命令退出码。
- **证据图必须体检**：`screenshot` 带 `minBytes`（例如 15000）。屏幕熄灭、窗口被挡、整帧全黑时 PNG 只有几 KB，看起来“拍成功”了，插进报告才发现是白图。生成文档后再核对一遍每张图的大小与文档里的图片页分布。
- 结论与证据分开写：先给结果，再给验证方式。

## 6. 长任务工程化

- 三层小工具，坐标从几何断言里取，不要散落在每个脚本里：
  - **预检**：窗口枚举、模态检查、几何断言、输入自检
  - **语义层**：tooltip/列表导出、控件树查询
  - **操作层**：点击、输入、截图、读回
- 一次性脚本用完即弃，不进仓库；能复用的落成 `computer` 的 action 或 `test/` 里的用例。
- 单次动作一次进程调用，卡住可杀，超时默认 30s。

---

## 7. 沟通节奏

- 连续几步没有进展就同步：**卡在哪、下一步试什么、需要什么信息**。不要闷头自查几十步。
- 工具自身出问题（视觉不可用、注入失效）**立刻说**，别让用户从结果里猜。
- 用户一句纠正往往顶一小时试错，听到就停下来改方向。
